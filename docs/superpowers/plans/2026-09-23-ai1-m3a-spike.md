# AI1 M3a Spike: Playwright Through Orca's One-Tab CDP Proxy

This is a facts file. A throwaway spike produced it. The spike code is not
in the repository. This file is the only kept output.

The spike bundled `cdp-ws-proxy.ts` from the Orca repository with esbuild,
loaded it in a hidden Electron window (`show: false`, no `show()` call, dock
hidden), and pointed it at one `<webview>` guest that loads a local test
page. A visible-window check ran after every start. Each check found 0
Electron windows on screen.

## Question 1: Does plain Playwright work through the proxy?

Command: `chromium.connectOverCDP(proxyUrl)`, then `page.click("#go")` and
`page.goto(secondUrl)`.

**First run, unmodified proxy.** `connectOverCDP` did not throw. But
`browser.contexts()[0].pages()` was empty:

```
contexts 1 pages [ 0 ]
PROBE ERROR TypeError: Cannot read properties of undefined (reading 'click')
```

The proxy client sent these CDP methods, in this order:

```
Browser.getVersion
Target.setAutoAttach
Browser.setDownloadBehavior
Target.getTargetInfo
```

`Target.setAutoAttach` is the method Playwright's `connectOverCDP` uses to
find the existing page. The proxy's target-discovery class does not answer
this method locally. It falls through to the real per-page Electron
debugger, which returns a normal reply but never sends the
`Target.attachedToTarget` event that Playwright needs to build a `Page`
object. Result: Playwright sees one browser context, but no page in it.

**Second check: does `browser.close()` send `Browser.close`?** A separate
run called `connectOverCDP` then `browser.close()` right away. No new CDP
line appeared in the log. `browser.close()` on a `connectOverCDP` connection
does **not** send `Browser.close` to the proxy. It only closes the
WebSocket. This matches Playwright's own documented behavior: closing a
CDP-attached browser disconnects the client; it does not shut down the
real browser.

**Third check: what does it take to make Playwright find the page?** The
spike patched the proxy to answer `Target.setAutoAttach` locally and push a
synthetic `Target.attachedToTarget` event. Three problems came up, in
order, each one blocking the next:

1. The event needs a `browserContextId` field. Playwright's internal
   handler asserts on it (`assert(targetInfo.browserContextId, ...)`) and
   throws if it is missing. Any non-empty string works; Playwright falls
   back to its default context when the id is not one it already tracks.
2. The reply to `Target.setAutoAttach` must carry back the same `sessionId`
   the request carried, when the request had one. Playwright's `CRPage`
   sends a second, page-scoped `Target.setAutoAttach` after the first one.
   Skipping the session-id echo (by not calling
   `responder.recordRequestSessionId` before the reply) misroutes that
   second reply and Playwright throws an assertion error.
3. With both fixes in place, `browser.contexts()[0].pages()` reports
   **one page** — the CDP-method gap from problem 1 above is closed. But
   the page itself does not work yet: `page.url()` reads back as an empty
   string, and `page.title()` times out. `page.click("#go")` also times
   out waiting for the `#go` locator, because Playwright is still waiting
   for the page to finish initializing.

So: `connectOverCDP` resolves through the proxy, and the CDP methods it
sends are `Browser.getVersion`, `Target.setAutoAttach`,
`Browser.setDownloadBehavior`, `Target.getTargetInfo`, then (once a page
session exists) `Page.enable`, `Page.getFrameTree`, `Log.enable`,
`Page.setLifecycleEventsEnabled`, `Runtime.enable`,
`Page.addScriptToEvaluateOnNewDocument`, `Network.enable`, a second
`Target.setAutoAttach`, `Emulation.setFocusEmulationEnabled`,
`Emulation.setEmulatedMedia`, `Runtime.runIfWaitingForDebugger`. None of
these throw a protocol error. But finding the page needs the
`Target.setAutoAttach` local answer above, and even with it, a working page
(one that answers `page.url()`, `page.title()`, `page.click()`) is not yet
proven. See "Changes for Task 8" for the exact shape and for the open risk.

## Question 2: What does Playwright MCP send, and which local answer works?

Command: Playwright MCP (`@playwright/mcp`, `--cdp-endpoint`) through the
Model Context Protocol SDK, calling `browser_navigate`, `browser_snapshot`,
`browser_navigate` again.

**Unmodified proxy.** Playwright MCP sends `Target.createTarget` (three
times, once per failed tool call). The proxy's target-discovery class does
not answer this method locally either. It forwards to the real per-page
debugger, which returns a CDP protocol error:

```
Protocol error (Target.createTarget): Not supported
browser_navigate {"isError":true,...": "Not supported"}
browser_snapshot {"isError":true,...": "Not supported"}
browser_navigate {"isError":true,...": "Not supported"}
```

**With the plan's own local answer for `Target.createTarget`
(`{ targetId: "orca-proxy-target" }`), and nothing else.** This is the
answer that the current Task 8 draft (`cdp-target-discovery.ts`, ported and
changed) already gives. All three tool calls still failed, this time with a
different, silent error:

```
TypeError: browserBackend.callTool: Cannot read properties of undefined (reading '_page')
```

Answering the RPC alone is not enough. Playwright's internal target
tracking needs the `Target.attachedToTarget` event (see Question 1) paired
with the RPC reply, not just the reply by itself.

**With the full fix from Question 1 (`Target.setAutoAttach` answered
locally, with the synthetic event and correct session-id echo).**
Playwright MCP found the existing page through `Target.setAutoAttach` and
did not need to call `Target.createTarget` at all. But `browser_navigate`
then failed with a different error:

```
Error: browserBackend.callTool: Frame has been detached.
```

`browser_snapshot` then timed out. This lines up with a comment already in
Orca's own proxy code: "Electron webview CDP subscriptions silently lapse
after cross-process swaps." A plain, generic `Page.navigate` (which is what
a fresh CDP client sends before the proxy's `navigateWithLifecycle` special
case even matters, at the `Target`/frame-tracking layer above it) does not
survive a real navigation of the guest the way a real Chrome tab would.

So, to directly answer the question asked: **neither of the two answers
tested — the existing target id alone, or the forwarded error — makes the
three tools work.** Making the tools work needs the `Target.setAutoAttach`
local answer plus the synthetic event (Question 1), and even then,
navigation across the guest's process swaps needs more work that this
spike did not finish. See "Changes for Task 8".

## Question 3: Does Playwright keep the path prefix?

A plain HTTP server (not Orca's proxy) answered `/secret-part/json/version/`
with a `webSocketDebuggerUrl` of `ws://127.0.0.1:<port>/secret-part/devtools/browser`.
`chromium.connectOverCDP("http://127.0.0.1:<port>/secret-part/")` then ran
against it.

Output:

```
HTTP /secret-part/json/version/
UPGRADE /secret-part/devtools/browser
connect ended (expected): Error: browserType.connectOverCDP: WebSocket error: socket hang up
```

Playwright requests exactly `/secret-part/json/version/` for HTTP
discovery, and then opens the WebSocket at exactly the path from
`webSocketDebuggerUrl` (`/secret-part/devtools/browser`), unchanged. The
prefix survives both steps. The connection then failed because the test
server closes the socket right after the upgrade, on purpose — that is not
a fact about Playwright.

**Answer: yes.** The `/<secret>/` prefix works for both HTTP discovery and
the WebSocket URL, with no change needed.

## Question 4: OpenCode's MCP config entry for a local command server

Read with `opencode --help` and `opencode mcp --help` and
`opencode mcp add --help` only (no owner config file read, no service
change). `opencode mcp add` takes a name and a command after `--`, with
`--env key=value` for environment variables and `--global` for the global
config instead of the project config. The `--help` output does not print
the JSON schema itself, so the exact key names come from OpenCode's public
documentation and its published config schema (`opencode.ai`), cross-checked
against each other:

```json
{
  "mcp": {
    "<server-name>": {
      "type": "local",
      "command": ["<executable>", "<arg1>", "<arg2>"],
      "enabled": true,
      "environment": { "KEY": "value" }
    }
  }
}
```

`type` and `command` are required. `type` is the string `"local"`.
`command` is an array of strings. `enabled` is a boolean. `environment` is
an object of string values (optional). `cwd` (string) and `timeout`
(integer, milliseconds) are also optional and were not needed here.

**Answer: this matches the shape already in the Task 8 draft's
`mcp-config.ts` exactly** (`type: "local"`, `command` as an array,
`enabled: true`). No change needed for Question 4.

## Changes for Task 8

1. **`Target.setAutoAttach` needs a local answer. It does not have one
   today.** Add it to `cdp-target-discovery.ts`'s `handleCommand`, next to
   the existing `Target.setDiscoverTargets` branch:
   - Answer the RPC with `{}`.
   - When the request has no `sessionId` (the root-level call, not the
     later page-scoped one from `CRPage`), also push an unsolicited
     `Target.attachedToTarget` event to the client:
     `{ method: "Target.attachedToTarget", params: { sessionId: <a session id from CdpSyntheticSessionRegistry.attachPageSession()>, targetInfo: <the same shape buildTargetInfo() returns, plus a browserContextId field with any non-empty string>, waitingForDebugger: false } }`.
   - When the request has a `sessionId` already (the page-scoped call),
     answer `{}` only. Do not send a second event.
   - Whichever branch answers, first record the request's own `sessionId`
     the same way the existing code does
     (`responder.recordRequestSessionId`), so the RPC reply carries the
     right `sessionId` back. Skipping this breaks the second,
     page-scoped `Target.setAutoAttach` call.
   - This changes the existing `Target.createTarget` test at Task 8 Step
     2, and the answer in Step 3: `Target.createTarget`'s reply also needs
     the `browserContextId` field on any target info it returns, and,
     for a client that expects auto-attach, the same kind of
     `Target.attachedToTarget` event alongside the RPC reply. Otherwise
     `Target.createTarget` on its own point-blank fails with a client-side
     "Cannot read properties of undefined" error, as this spike found.

2. **Open risk, not resolved by this spike: real navigation and page
   interaction over this proxy still fails.** Even with the fix in item 1,
   `page.url()`, `page.title()`, and `page.click()` did not work in a plain
   Playwright connection, and Playwright MCP's `browser_navigate` failed
   with "Frame has been detached." This did not come from an unanswered
   CDP method (nothing errored as unsupported) — it looks like a mismatch
   between how Playwright's frame-tracking expects a page's `Target` and
   frame identity to stay stable across a navigation, and how an Electron
   `<webview>` guest actually behaves across a cross-process navigation
   (Orca's own code has a comment about exactly this: CDP subscriptions
   lapse after these swaps). Task 8 needs its own dedicated test for real
   navigation through the finished agent-address server (its Step 15 e2e
   test, "Playwright controls the agent tab... sees only that page",
   already does a `page.goto` and a `page.click`) and must not assume the
   `Target.createTarget` answer by itself is enough. Budget time to
   diagnose this further if that e2e test fails the same way.

3. **The `/<secret>/` path prefix design is correct. No change.** The
   agent-address server's `stripSecret` handling, for both the HTTP
   `/json/version` answer and the WebSocket upgrade check, already matches
   how Playwright actually requests and uses these paths.

4. **The OpenCode MCP config shape in `mcp-config.ts` is correct. No
   change.** `{ mcp: { "<name>": { type: "local", command: [...],
   enabled: true } } }` matches OpenCode's own schema.

5. **`browser.close()` does not send `Browser.close` to the proxy.** A
   Playwright client that disconnects with `browser.close()` only closes
   its WebSocket; it does not ask the proxy to close the AI1 tab. This
   spike did not find a case where `Browser.close` reaches the proxy. The
   plan's Task 9 note about checking that the AI1 tab survives
   `browser.close()` is still worth keeping as a regression test, but the
   risk it guards against did not appear in this spike.
