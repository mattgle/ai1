# AI1 design

Date: 2026-09-21
Status: approved design, before the M1 implementation plan

AI1 means "All In 1". It is a personal desktop IDE for work with coding agents
across a meta-repo: one folder that contains many sibling git repositories.

## Goal

One app gives these functions:

- A file explorer of the workspace root, with Material icons.
- A view of the repositories that have uncommitted changes, with their files.
- A center area with tabs for a code editor, file diffs, terminals, and a browser.
- Full TypeScript IntelliSense and ESLint fix on save in the editor.
- Coding agents that run in terminals and continue when the app is closed.
- A list of all agents with their status.

## Constraints

- **No moving upstream to merge.** AI1 is not a fork of a product. All
  third-party code comes in as dependencies with pinned versions. An upgrade is
  a version change on a day the owner chooses.
- **A daily version check** for the tools that AI1 runs. The check tells the
  user. It installs nothing without a user action.
- **Freedom of choice.** The user can add or remove editor extensions from
  inside the app.
- **Platform:** macOS on arm64. Other platforms are out of scope.
- **Agent:** OpenCode, in a terminal. AI1 has no agent-specific integration.

## Out of scope

- Debugger, notebooks, collaboration, remote development, dev containers.
- The AI features that are built into Theia.
- Use of the browser pane for general browsing with logins.
- Windows, Linux, and x64 builds.
- Distribution to other users, notarization, and a Developer ID signature.

## Decisions and their reasons

| Decision | Reason |
|---|---|
| Base: Eclipse Theia, as pinned `@theia/*` npm packages | Theia is a framework for custom IDEs. It has an extension host that runs VS Code extensions. So IntelliSense, ESLint, Material icons, and the changes view need no code of our own. It is a dependency, not a fork. |
| Not a fork of an agent IDE product | A fast upstream makes each rebase expensive, and most of its features are not used. |
| Not an app built only from small libraries | The language-server bridge, ESLint on save, the explorer, and tab management are then our code to write and maintain. The estimate is 4 to 6 times the work. |
| Changes view: native AI1 code, a Theia extension of our own | The two main panels of AI1 have no VS Code extension layer. The owner controls how they look and behave. The git logic comes from the MIT-licensed `metarepo-sc` VS Code extension of the same owner and is rewritten for the Theia API. |
| Material icons: native AI1 code, with the pinned npm package `material-icon-theme` | The npm package ships the icon manifest and the SVG files. Native code registers the theme. No icon extension is downloaded. |
| Language extensions (TypeScript, ESLint, and others): from Open VSX | They give IntelliSense and lint with no code of our own. The Microsoft Marketplace terms permit use only from Microsoft products. |
| Agents: the OpenCode service is the source; shells persist through tmux | Replaced on 2026-09-22 by the M2 design (`2026-09-22-ai1-m2-agents-design.md`). OpenCode v2 runs as a service that owns the sessions and gives their status. Herdr is not a part of AI1. |
| Updates: tell the user, one action to apply | A silent update of a tool that runs agents on source code is a risk. |

Theia uses the EPL-2.0 license. Our own extensions can have any license. Only
changes to Theia's own files carry a share obligation, and only on
distribution.

## Architecture

One Electron app. The Theia generator makes a monorepo with one application
package and one Theia extension for each job that Theia does not do.

```
ai1/
├── applications/electron/   the app: pinned @theia/* packages, packaging config, application defaults
│   └── plugins/             build output: bundled VS Code extensions (not in git)
└── extensions/
    ├── shell-layout/        default layout, Settings layout, AI features off
    ├── changes-view/        repositories with changes, their files, diffs, discard
    ├── material-icons/      Material file icons from the pinned npm package
    ├── agents/              OpenCode sessions, terminal tabs, Agents view (M2)
    ├── browser-pane/        web view tab with agent control
    └── updater/             daily version check
```

The plugins folder is inside the application package. The packaged app and the
development app then find it with the same relative path.

### The changes view

| Part | Side | Function |
|---|---|---|
| Pure logic | Node back end | Parses `git status --porcelain` lines (renames included), makes the status letter, filters paths that must not start a refresh, and selects the discard command. Unit tests cover it. |
| Changes service | Node back end | Finds the git repositories that are direct children of a workspace root (or the root itself). Runs `git status --porcelain --untracked-files=all` on all of them in parallel. Reads a file at `HEAD`. Does the discards. The front end calls it through Theia's RPC channel. |
| Changes widget | Front end | A tree in the right area. Repository rows show the name and the branch. File rows show the file icon, the folder, and the status letter. Only repositories with changes show. Toolbar: refresh, expand all, collapse all. Row actions: open file, discard changes, discard all changes, each discard with a confirm dialog. |
| Diff | Front end | A resource resolver gives the `HEAD` content under its own URI scheme. A click on a file row opens Theia's diff editor: `HEAD` against the working file. A renamed file reads `HEAD` at its old path. An untracked file opens as a normal file. A deleted file opens its `HEAD` version alone, read-only. No temporary file is written. |
| Refresh | Front end | File change events, filtered, with a 500 ms debounce. Also when the widget becomes visible. |

Discard rules: an untracked file is deleted. A rename is undone with
`git restore --source=HEAD --staged --worktree -- <old> <new>`, whichever
status column carries the `R`. Every other tracked file uses
`git restore --source=HEAD --staged --worktree -- <file>`, the same command
with one path: it also removes a staged new file, which has no HEAD version.
A copy discards only its own path, never the source it copied from. In a
repository with no commits yet, `restore --source=HEAD` cannot resolve HEAD;
that discard uses `git rm --cached --quiet -- <file>` and then deletes the
file, the same result. Discard all uses `git reset --hard HEAD` and then
`git clean -fd`, without `-x`, so ignored paths stay.

### Project setup

| Item | Value |
|---|---|
| Theia | `1.75.0`, all `@theia/*` packages at this exact version |
| Electron | `42.8.1`, the exact version that Theia 1.75 requires |
| Node | 24 |
| Package manager | npm, with workspaces |
| Scaffold | `generator-theia-extension`, minimal Electron application |
| Packaging | electron-builder, arm64, ad-hoc signing |
| Remote | private GitHub repository |

The build downloads the language extensions from Open VSX into the plugins
folder. The npm package `material-icon-theme` is pinned at `5.38.1`.

Rules for the custom extensions:

- Each extension has one purpose.
- No custom extension depends on a different custom extension.
- `agents` depends only on the OpenCode and tmux binaries.
- `browser-pane` depends only on Electron.

### Theia packages in the app

Core, editor, Monaco, navigator, file system, workspace, terminal, SCM, search
in workspace, preferences, keymaps, markers (Problems), outline, file search,
messages, the VS Code extension host, the Open VSX registry view, and Electron.

### Bundled VS Code extensions

- Built-in language support: TypeScript and JavaScript language features, JSON,
  CSS, HTML, Markdown.
- Built-in Git extension. It gives the git colors in the explorer.
- `dbaeumer.vscode-eslint`

The VS Code extension host of Theia 1.75 depends on `@theia/ai-core`, so that
package loads. Its default activation service is always active, and no
preference controls it. `shell-layout` replaces that service with one that is
always off, so AI1 shows no Theia AI user interface.

### Layout

```
┌──────────┬────────────────────────────────┬──────────────┐
│ EXPLORER │  editor │ diff │ term │ browser │ Changes│Agents│
│          │                                │              │
│ Material │        center tab area         │ dirty repos  │
│ icons    │       (Theia "main" area)      │  └ files     │
│          │                                │              │
├──────────┴────────────────────────────────┴──────────────┤
│ Problems (TypeScript and ESLint errors), closed by default │
└───────────────────────────────────────────────────────────┘
```

`shell-layout` implements `initializeLayout`. Theia calls this method only when
no saved layout exists. So the default applies on the first start, and later
manual changes stay.

`changes-view` opens its own widget in the `right` area through its view
contribution. `shell-layout` closes the Source Control view of Theia in the
default layout, opens the explorer in the `left` area, and leaves Source
Control available from the View menu.

### Default preferences

The application defaults live in `theia.frontend.config.preferences` of the
Electron app, Theia's standard place. They apply before the first start
completes, a change of a default applies on the next start, and the user
settings file holds only user choices. The defaults: format on save with the
ESLint formatter (`eslint.format.enable` on, because the ESLint extension
registers its formatter only then). ESLint fix on save, as a boolean value;
Theia 1.75.0 has no `explicit` mode. Tab size 2. No minimap. Sticky scroll on,
in the editor; Theia 1.75.0 has no sticky scroll preference for trees.
Preview tabs off. Whitespace changes shown in diffs. Dark theme. Material icon
theme. Workspace trust off.

## Milestones

Each milestone has its own spec, plan, and build cycle. Each one ends with an
app that the user can use.

### M1: skeleton

Own code: `shell-layout`, `changes-view`, `material-icons`.

M1 is complete when all of these are true:

1. The app opens a meta-repo folder as the workspace root.
2. The explorer on the left shows Material icons.
3. The Changes view is on the right on the first start. It lists only the
   repositories that have changes.
4. A click on a changed file opens the diff in the center.
5. Go-to-definition and autocomplete work inside a TypeScript repository of the
   workspace.
6. A save runs the ESLint fixes of that repository.
7. One script makes a packaged arm64 app and installs it in `/Applications`.
   The script uses ad-hoc signing and never uses automatic certificate
   discovery.
8. Lint and type check pass.

To measure in M1: the file watcher load on a root with many sibling
repositories.

### M2: agents

See `2026-09-22-ai1-m2-agents-design.md`. It replaces the earlier text of this
section: the source of the agent data is the OpenCode service, and Herdr is not
a part of AI1.

### M3: browser

Own code: `browser-pane`.

- A center tab with an Electron web view, a URL bar, back, forward, reload, and
  DevTools.
- The web view uses its own session partition, apart from the IDE.
- OpenCode controls the pane through an existing MCP server (Playwright MCP or
  Chrome DevTools MCP) on the Chrome DevTools Protocol. AI1 contains no browser
  automation code.
- **Open security point, to resolve in the M3 spec.** A debugging port for the
  full app also exposes the IDE window to each local process. The IDE window
  can read and write all files. The M3 design must limit access to the browser
  pane only.

### M4: updater

Own code: `updater`.

- It checks on start and then each 24 hours.
- It checks OpenCode, tmux, the bundled extensions (through Open VSX), and AI1
  itself.
- It tells the user. One user action applies an update. Nothing installs
  silently.
- An app with ad-hoc signing cannot use the standard macOS auto-update method.
  "Update AI1" means: pull, build, and replace the app through the build
  script.
- Library versions (Theia, Electron) are not a task of the updater. Renovate or
  Dependabot opens a pull request in the repository, and the owner accepts it
  or ignores it.

## Error behavior

| Case | Behavior |
|---|---|
| OpenCode or tmux is not installed | The Agents view shows the install command. The rest of the app works. |
| Event stream lost | Reconnect with increasing wait time, then a full load. See the M2 design. |
| Pane input owned by a dead client | Attach again with `--takeover`. |
| Browser page fails to load | Error page in the tab with a retry button. |
| Extension host stops | Theia starts it again. This is built-in behavior. |

## Tests

- Unit tests for the OpenCode client against a fake HTTP server: requests,
  events, a lost connection. See the M2 design.
- Unit tests for the version comparison of the updater.
- One end-to-end smoke test for each milestone with Theia's Playwright package.
  The M1 test opens a fixture meta-repo and checks the M1 criteria that a test
  can check.
- Gates on each change: ESLint, type check, unit tests.

## Verified facts

- Theia community release 2026-02 supports VS Code extension API 1.108.
- Theia has a native icon theme registry (`IconThemeService.register`), and its
  parser for the VS Code icon theme format is a class that other code can use.
- OpenCode v2 runs as a background service that owns the sessions; its
  interface is a client of that service. The M2 design lists the verified API
  facts.
- `initializeLayout` in Theia runs only when no saved layout exists.

- `AIActivationServiceImpl` in `@theia/ai-core` 1.75.0 sets `isActive = true`.
  The `ai-features.AiEnable.enableAI` preference exists only in `@theia/ai-ide`.
- Theia 1.75.0 builds with esbuild, not webpack.
